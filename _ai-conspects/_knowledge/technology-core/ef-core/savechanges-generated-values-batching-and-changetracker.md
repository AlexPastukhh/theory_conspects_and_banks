# EF Core SaveChanges generated values, batching, and ChangeTracker.Clear

Knowledge ID: `ef-core.savechanges-generated-values-batching-and-changetracker`

Topic: `ef-core`

## Generated values

Generated values can be database-generated during INSERT/UPDATE or provider/client-generated before INSERT. EF can populate generated values back into tracked entities after SaveChanges.

Common generated value sources:

- Identity/auto-increment keys (database-generated during INSERT)
- Database sequences (database-generated)
- Database default constants (database-generated)
- Provider/client-generated values (generated before INSERT)

Database SQL defaults are distinct from constant defaults. For example, SQL Server can evaluate the expression during insert:

```csharp
entity.Property(o => o.CreatedAt)
    .HasDefaultValueSql("SYSUTCDATETIME()")
    .ValueGeneratedOnAdd();
```

SQL Server has no special pseudo-table named `generated`. `OUTPUT INSERTED.SomeColumn` returns values after an insert or update, while `OUTPUT DELETED.SomeColumn` returns values before a delete or update. The `INSERTED` row can therefore contain identity, default, computed, and `rowversion` values after the database has produced them, allowing EF to populate the tracked entity.

Computed and trigger-generated properties must describe their generation timing in the EF model:

```csharp
entity.Property(o => o.Total)
    .HasComputedColumnSql("[Subtotal] + [Tax]", stored: true)
    .ValueGeneratedOnAddOrUpdate();

entity.Property(o => o.AuditCode)
    .HasMaxLength(100)
    .ValueGeneratedOnAddOrUpdate();

entity.HasTrigger("TRG_Orders_SetAuditCode");
```

An updated-at property illustrates the mechanism boundary: `HasDefaultValueSql("SYSUTCDATETIME()")` supplies the insert value, but update behavior normally needs a trigger or computed expression. SQL Server `rowversion` is configured with `IsRowVersion()` and is generated by the database on writes.

GUID generation can instead happen before SQL is sent. With the SQL Server provider, a GUID key configured as generated-on-add normally uses the provider's sequential GUID generator. A non-primary GUID property can request the same generated-on-add behavior with `ValueGeneratedOnAdd()`. This is provider/client generation, unlike identity, defaults, computed values, `rowversion`, sequence defaults, and trigger-generated columns that arise when database SQL executes.

For parent/child graph inserts, EF can often insert everything in one SaveChanges and fix up generated keys through relationship fix-up. However, you may need an intermediate SaveChanges when a later step needs a generated ID outside EF relationship fix-up, such as when passing the ID to another system or performing a non-EF operation.

## Batching for large imports

One giant SaveChanges for huge imports creates memory, change-tracker, and error-recovery problems. SaveChanges per row is usually worst; chunked SaveChanges is the practical compromise.

Considerations for large imports:

- Large imports accumulate many tracked entities in memory
- One huge SaveChanges may create a very large transaction
- Error recovery is harder when everything is in one batch
- Chunked SaveChanges provides better memory management and error isolation

## ChangeTracker.Clear and short-lived DbContext

SaveChanges alone does not reduce memory. ChangeTracker.Clear or disposing a short-lived DbContext does.

ChangeTracker.Clear is a big hammer: it clears everything tracked by that context. Use it when you want to explicitly detach all entities and reset the context to a clean state.

Fresh DbContext per chunk or separate contexts for separate phases avoid accidental detach bugs. This pattern is especially useful for batch processing where you want to:

- Process a chunk of data
- Save changes
- Clear or dispose the context
- Start fresh for the next chunk

Short-lived DbContext patterns:

- Create a new DbContext for each unit of work
- Use using/await using to ensure proper disposal
- This naturally limits memory growth and change tracker size
- Avoids stale state between operations

## Manual savepoints for business phase boundaries

Manual savepoints are useful when rollback boundaries are business phases, not every SaveChanges call. This is a complementary pattern to AutoSavepointsEnabled when you need explicit control over savepoint placement.
